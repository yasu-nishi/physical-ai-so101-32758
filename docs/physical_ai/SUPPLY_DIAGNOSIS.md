2026-11-01、腕を停止して保持したまま、モーターへ書き込まずに電圧と通信を調べた。**手首・グリッパーのサーボ自身が電圧エラーを返すことを再現した。** 一致する単独読取りへの応答で、グリッパーが3.7Vと電圧エラービット1を同時に返した記録がある。応答のID・長さ・チェックサムは正常だった。

## 通信側で見つけた問題と修正

導入済みのLeRobot v0.5.1とfeetech-servo-sdk 1.0.0を確認した。SDKのグループ読取りは各サーボの応答エラーフラグを捨てるため、通信成功とサーボ正常を同一視できない。また読取り要求のデータ長を厳密には照合していない。診断コードはID・データ長・チェックサム・エラーフラグを調べ、異常時の生データを保存する。

グループ読取りを途中で拒否すると、後続サーボの古い応答が受信側へ残ることがある。SDKの`clearPort()`が呼ぶ`serial.flush()`は入力を消去しない。このため、最初の診断では中断後に長さ不一致とID不一致が各1件発生した。診断コードへ失敗した読取りの待ち時間とホスト入力バッファの消去を追加した。動作の再試行や停止解除はしない。

修正後は応答形式の不一致がなくても、サーボ電圧エラーが2件発生した。通信上の不一致だけですべてを説明することはできない。生パケットは要求レジスターを返信しないため、単に観測した全フレームを電圧値として集計しない。完了した読取り結果と、一致する単独読取りの電圧エラー応答を使う。

## 再起動後の確認

操作者の再起動報告後、古いシリアル接続が`Device not configured`となった。旧プロセスを終了し、排他ロックを取り直して6モーターへ再接続した。実測の校正レジスターは既存校正と一致し、全6モーターのトルク、目標位置、速度設定は0に戻っていた。保持トルクが継続しているとは扱わない。

`--after-restart`で新しい読取り専用基準を取得する機能を追加した。この指定は以前の姿勢・トルク状態の継続を仮定しないためのもので、動作再開やモーター書込みを許可する機能ではない。通信失敗時に古い`stopped_holding`表示を残さず、`feedback_unverified`を表示する修正も加えた。再起動後の60.13秒・291標本で、全トルクOFFのまま手首rollから2件、グリッパーから3件の電圧エラー応答が発生した。応答形式異常は0件。記録済みの関節・目標・トルクは基準から変化しなかった。全トルクOFFを最終確認して診断接続を閉じた。動作を再開するプロセスは起動していない。

## 再現と現在の停止状態

操作者から「できるとこはした」と接点確認の報告を受けた後にも、グリッパーの電圧エラーを再現した。どのコネクターを操作したか、電源を再投入したかは独立には確認していない。この最初の再検査は旧`--after-restart`オプションで新しい基準を取得したため、その名前を電源再起動の証拠に扱わない。公開集計の`operator_context`にこの制約を記録した。

続いて`--fresh-baseline --unicast-only --sample-hz 0.5`で、グループ読取りを使わず2秒ごとに6モーターを個別に調べた。この条件でも手首rollの`Status`読取り応答に、応答エラーフラグ1とレジスター値1が同時に入っていた。別に読んだ電圧値は4.8–4.9Vだったが、異常フラグを打ち消す証拠にはしない。読み取り方式と頻度を変えても異常が残ったことを確認した範囲であり、電源・配線・サーボ内部の原因箇所は未特定である。全6モーターのトルクOFFを確認して診断を終了した。

操作者が追加で提示したACアダプターのラベルから、公称出力5.0V・4.0A・20Wを確認した。続いて制御基板の別電源プラグを差し直したとの報告を受けて再検査した。写真は公開物に含めない。ラベルの定格は実測した電源電圧や手先の電圧ではなく、電源単体の故障・正常を断定する根拠にはしない。[LeRobotの接続手順](https://huggingface.co/docs/lerobot/en/so101)では、USBと電源を制御基板へ接続する構成が示されている。異常を回避するために電圧を上げたり監視閾値を緩めたりしない。

電源プラグの差し直し後も60.18秒で電圧エラー応答4件を取得した。手首rollへの単独の電圧読取りで、3.9Vと電圧エラーフラグ1を同時に返した応答を保存した。これはサーボ内部センサーの報告で、外部テスターの実測ではない。全トルクOFFでの読取りのみを行い、位置目標・速度・トルクの書込みは0。全モーターのトルクOFFを最終確認して接続を閉じた。現時点では、同じ適合仕様の正常電源との比較、または供給元・手先の電圧実測による切り分けが残っている。

`scripts/diagnose_real_hold.py`は、停止済みの旧プロセスがシリアルを閉じた後にだけ起動できる。ローカルの排他ロックを取得し、送信直前にPING・READ・SYNC_READ以外の命令を拒否する。WRITE・REG_WRITE・ACTION・SYNC_WRITEを出す経路はない。トルクを解除せず、停止を解除せず、MCPの実機動作を有効化しない。

```sh
uv run --locked python scripts/diagnose_real_hold.py \
  --config config/physical_ai/real_staged.local.json \
  --previous-run artifacts/previous_stopped.local \
  --run-dir artifacts/supply_check.local --capture-seconds 60
```

操作者が電源再起動を報告した後の確認では、上記に`--after-restart`を加える。通信不能からの自動再接続・自動動作再開は行わない。

接点確認など、再起動を断定しない操作の後は`--fresh-baseline`を使う。読取り方式の切り分けは`--unicast-only --sample-hz 0.5`で行える。いずれもシリアル送信段階の書込み禁止は維持する。

旧プロセスはSTOPで停止を確認し、`EXIT`を置いて終了を確認してから起動する。同時に2つのプロセスでシリアルを開かない。5Hzの詳細記録が終わると1Hzの読取り監視へ移り、状態と追加の異常を保存する。新しい出力先に`EXIT`を置くかCtrl-Cで終了できる。監視終了は保持トルク解除を意味しない。

センサー報告の電圧異常が再現しているため、現在は動作再開をしない。次の現物確認は、腕を支えて電源を切った状態で、電源入力と手首・グリッパーの3ピンコネクターの緩みを調べること。切り分けには必要に応じて供給元と手先側の電圧を実測する。保持トルクが入った状態で配線を差し直さない。電圧や停止閾値を上げ下げして試行を通さない。

厳密な応答検査を初期姿勢調整CLIにも接続した。調整中の読取りでエラーフラグを検出すると、次の移動指令へ進めず停止する。異常の生パケットを`feedback_faults.jsonl`へ保存し、位置・トルク・保持目標を確認できない場合は`stopped_hold_unverified`と表示する。診断専用の`AuditedReads`は引き続き全書込みを遮断し、調整用の`CheckedReads`は既存の限定された書込み処理に応答検査を追加する。速度・追従・電圧の停止条件は変更していない。

通信監査19件、初期調整31件、既存実機アダプター2件を含め、全体133件が成功した。今回修正した初期調整CLIは模擬通信で検証し、異常が残る実機での動作再試行は行っていない。テストは実機動作成功の代わりにはならない。追加診断のモーター書込みは0、初期調整の累計は引き続き位置目標29・トルク有効化5・速度設定10である。

## 予備電源・テスターがない場合の次の比較

操作者から、予備の5V電源と電圧計のどちらもないとの回答を得た。既存の制御基板・電源・ケーブルで、ID6だけを直結して途中のモーターと配線を外す比較を準備した。**単独接続の実機試験はまだ実施していない。**

その後、操作者から直結作業は実施できないとの回答を得た。この手順は今回の実行依頼から外し、未実施のまま保留する。配線変更やARMの再入力を繰り返し求めず、動作サーバー停止を維持した。以下は後日、実施可能な環境が整った場合の参考手順である。

1. 腕を安定した姿勢で支え、モーター電源を切る。通電中に3ピン配線を抜き差ししない。
2. 制御基板から腕へ出る既存の3ピンケーブルを、グリッパーモーター（ID6）へ直接接続する。ID6に元からつながっていたID5側の線は外し、基板から給電するのはID6だけにする。コネクターの向きは変えない。ケーブルが無理なく届かない場合は実施しない。
3. 元と同じ電源を入れ、次の読取り専用診断を実行する。ARM、キャリブレーション、`setup_motors`は実行しない。ID・設定を書き換える必要はない。

```sh
.venv/bin/python scripts/compare_servo_reads.py \
  --config config/physical_ai/real_staged.local.json \
  --output artifacts/id6_direct_check.local \
  --motor-ids 6 --read-path individual --seconds-per-path 30 \
  --setup-label operator_reported_id6_direct
```

出力先は未使用の`.local`ディレクトリを指定する。CLIでID6を選ぶだけでは物理的な直結の証拠にならないため、接続方法は操作者の申告として区別して記録する。実装は選択したIDだけのLeRobotバスを作り、シリアル送信段階で書込み命令を拒否する。位置・トルク・電圧保護値は変更しない。単独IDの実際のSDK読取りパケットと書込み遮断を模擬通信で確認し、診断・監視の関連37テストが通過した。

直結でも異常が出れば、外した途中の配線だけでは説明できず、共通の電源・基板・ケーブル・ID6内部が候補として残る。直結で出なければ途中の経路や接続数の影響が疑われるが、30秒の無異常だけで解決とは判定しない。必要に応じて同じ直結ケーブルでID5を比較する。どちらの場合も、外部電圧測定や正常な同仕様電源との比較なしに、電源とサーボ故障を一意には判別できない。
